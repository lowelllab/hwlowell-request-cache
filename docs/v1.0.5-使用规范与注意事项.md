## 一、v1.0.5 变更概览

### 1. 多 Redis 集群手动切换

同一套 Laravel 应用需要访问多地 Redis 集群时，通过 `cluster()` 显式指定本次操作连到哪个集群：

```php
use HwlowellRequestCache\RequestCache;

// 未绑定：走 default_connection
$data = RequestCache::get('users', ['id' => 1]);

// 绑定广州集群读
$data = RequestCache::cluster('gz')->get('users', ['id' => 1]);

// 绑定香港集群写
RequestCache::cluster('hk')->set('users', ['id' => 1], ['name' => '张三'], 600);
```

绑定对以下 API 全部生效：`get`、`set`、`delete`、`mget`、`mset`、`remember`、`warm`、`clearGateway`、`clearAll`、`clearTags`。

### 2. 新增两个配置项

```php
// config/request_cache.php
'redis_cluster' => [
    'enabled' => true,
    'hash_tag' => 'request-cache',
    'cluster_safe_mode' => true,
    'scan_strategy' => 'all_nodes',
    'default_connection' => 'default', // 新增
    'connections' => [],               // 新增
],
```

- `default_connection`：未调用 `cluster()` 时，数据读写、当前连接清理、统计与监控使用的权威连接名，默认 `default`。
- `connections`：允许手动切换的连接名白名单，留空表示自动推导。

### 3. 稳定性修复（提交 `c2553de`，README 更新日志尚未收录）

这三项都会影响运行时行为，升级后建议重点回归：

- **SCAN 游标初始化**：phpredis 的 `scan()` 要求初始游标为 `null`，此前传入字符串 `'0'` 会被当成「迭代已结束」，导致 `clearGateway()` / `clearAll()` / `CacheMonitor` 的 SCAN 一个 key 都扫不到，**却仍然返回成功**。修复后新增 `RequestCache::initialScanCursor()` 与 `RequestCache::isScanCursorFinished()` 两个辅助方法，`RequestCache` 与 `CacheMonitor` 的扫描路径统一使用。
- **RedisManager 配置快照刷新**：Laravel 的 `RedisManager` 在首次实例化时会对 `database.redis` 配置做静态快照，`all_nodes` 策略运行时用 `Config::set()` 注册的节点连接不会被它识别。修复后在注册完全部节点配置后强制重建 Redis 单例，确保逐节点 SCAN 能真正连上每个 master。
- **集群 `ping()` 与错误捕获**：`RedisCluster::ping()` 需要传路由 key，此前无参调用会抛 `ArgumentCountError`；由于它是 `\Error` 而非 `\Exception`，原有的 `catch (\Exception)` 接不住，会直接冒泡到业务代码。修复后 `CacheMonitor` 按连接类型自动补路由 key，并将相关捕获统一放宽到 `\Throwable`。

## 二、使用规范

### 1. 配置分工：节点在 database.php，行为在 request_cache.php

`redis_cluster` 只控制本包的集群兼容行为，**不定义 Redis 节点**。节点列表、认证、连接复用一律配置在宿主项目的 `config/database.php`，由 Laravel Redis Manager 统一管理。本包不提供独立连接池，也不维护独立的集群节点列表。

```php
// config/database.php
'clusters' => [
    'default' => [
        ['host' => env('REDIS_LOCAL_HOST_1'), 'port' => 6379],
        ['host' => env('REDIS_LOCAL_HOST_2'), 'port' => 6379],
    ],
    'gz' => [
        ['host' => env('REDIS_GZ_HOST_1'), 'port' => 6379],
    ],
    'hk' => [
        ['host' => env('REDIS_HK_HOST_1'), 'port' => 6379],
    ],
],
```

集群带密码时，密码要放在 `clusters.options` 里，而不是塞进每个节点。放错位置会在建连阶段直接报 `Couldn't map cluster keyspace using any provided seed`：

```php
'clusters' => [
    'options' => [
        'password' => env('REDIS_CLUSTER_PASSWORD'),
    ],
    'hk' => [ /* 节点列表 */ ],
],
```

### 2. `enabled` 不是「仅控制 SCAN」的开关

这是最容易误读的一项，三种组合的实际行为：

- `enabled = false`：调用 `cluster()` 抛 `LogicException`；未绑定路径**仍然按 `default_connection` 工作**。也就是说，即使关掉多集群能力，你依然可以把 `default_connection` 指向任意一个连接名让整个应用读写它，只是不能在运行时切换。
- `enabled = true` + 未调用 `cluster()`：走 `default_connection`，`scan_strategy` 按配置值生效。
- `enabled = true` + 调用 `cluster('x')`：走 `x`，`scan_strategy` 强制降级（见第四节）。

### 3. 白名单推导规则

`connections` 留空时按以下规则自动推导：

- 顶层：只接收数组型连接，排除 `options`、`client`、`clusters`。
- `database.redis.clusters` 下：只接收数组值，显式排除 `options`。

如果显式写了非数组配置，直接抛 `InvalidArgumentException`，**绝不自动推导兜底**。生产环境建议显式列出白名单，避免误切到内部连接。

### 4. 锁与统计的连接归属：故意不同

| 能力 | 归属连接 | 原因 |
| --- | --- | --- |
| 分布式锁 | 跟随 `cluster()` 绑定的目标集群 | 锁保护的是目标集群上的写入，锁和数据必须同集群，否则跨机房并发写同一集群时锁形同虚设 |
| 统计计数 | 固定写 `default_connection` | 统计需要单一权威视角；`CacheMonitor` 的统计、趋势与单连接 Redis 信息也读这个连接 |

`CacheMonitor` 不支持运行时 `cluster('x')` 指定目标，但其默认监控连接遵循 `default_connection`。

### 5. LocalCache 按集群隔离，清理却是全量的

缓存 key 本身不含集群信息。为避免跨集群串用，本地缓存 key 用 `hash('sha256', 有效连接名) . ':' . key` 构造（不直接拼接连接名与分隔符，避免连接名含特殊字符时的边界碰撞），各集群在当前 PHP 进程内各持一份热点缓存。

但 `clearGateway()`、`clearAll()`、`clearTags()` 无论指定哪个集群，都会一次性 flush 掉进程内**所有**集群的本地缓存，确保清理后不残留任何集群的旧值。

## 三、实例语义：哪些方法返回克隆，哪些直接改当前实例

这一条 README 未展开，但通过 Facade 接入时最容易踩坑。

**`cluster()` 返回克隆实例**，绑定只在这条调用链上生效，用完即失效：

```php
public function cluster(string $name): static
{
    // 返回克隆实例而非 $this：request-cache 注册为容器单例，写在 $this 上会让绑定跨调用粘连
    $clone = clone $this;
    $clone->connectionName = $name;
    // ...
    return $clone;
}
```

**其余链式方法都返回 `$this`，直接修改当前实例**：`tags()`、`version()`、`sizeLimit()`、`encryptData()`、`enableStats()`、`setForceValidate()`。

后果是：通过 Facade 调用 `RequestCache::version('2.0')` 会改动容器单例，**影响此后同一请求生命周期内的所有调用**，而不是只影响这一次。

规范用法：

```php
// 不推荐：污染容器单例
RequestCache::version('2.0')->get('users', ['id' => 1]);

// 推荐：需要改变实例状态时自建实例
$cache = new RequestCache();
$data = $cache->version('2.0')->get('users', ['id' => 1]);

// cluster() 例外，它安全，可以直接在 Facade 上链式调用
$data = RequestCache::cluster('hk')->get('users', ['id' => 1]);
```

## 四、注意事项

### 1. 多集群的硬前提

`cluster()` 依赖「同系统多集群」这一前提：各地集群必须共用同一套 `APP_KEY`、`APP_NAME`、`APP_ENV` 与缓存 `version`，`generateKey()` 才能在各集群上算出逐字节相同的 key。任意一项不一致，跨集群读取必然 miss。跨系统访问不在本能力范围内。

### 2. 本包只提供切换机制，不提供跨集群策略

以下能力**明确不提供**，全部由调用方在业务代码中自行实现：

- 不提供自动兜底读取顺序：本地集群 miss 后不会自动去其他集群再读。
- 不提供自动回填：从远端集群读到数据后不会自动写回本地集群。
- 不提供删除广播与跨集群一致性保证。
- 不解析跨集群数据格式差异。
- 不内置跨集群调用的超时、熔断与并发控制。

兜底与回填需要自己编排：

```php
$params = ['id' => 1];

$data = RequestCache::get('users', $params);

if ($data === null) {
    $data = RequestCache::cluster('gz')->get('users', $params);
}

if ($data === null) {
    $data = RequestCache::cluster('hk')->get('users', $params);
}

// 回填就是一次普通写入
if ($data !== null) {
    RequestCache::cluster('default')->set('users', $params, $data, 600);
}
```

跨集群串行读取会拖慢主链路，务必自行控制尝试次数与超时。

### 3. `all_nodes` 适用范围很窄

只在**未调用 `cluster()`**、或**绑定名恰好等于 `default_connection`** 时生效。绑定其他集群时，运行时强制降级为 `single_connection`。

降级只发生在运行时的扫描路径上，**配置值本身不会被改写**——`config('request_cache.cache.redis_cluster.scan_strategy')` 读出来仍是你写进去的 `all_nodes`。排查清理范围问题时别被这个迷惑。

`all_nodes` 依赖宿主项目的 `database.redis.clusters` 配置，按 `default_connection` 的名字取出对应集群的节点列表逐节点 SCAN。节点解析失败时安全回退到当前连接，监控结果通过 `scope` 字段标注实际视角：`current_connection`（当前连接视角）、`cluster_aggregate`（全节点聚合）、`cluster_partial`（部分节点失败的聚合）。

### 4. 清理能力边界（最需要警惕）

> **绑定集群后，`clearGateway()` 与 `clearAll()` 只覆盖该集群的第一个 master 节点。**

Laravel 的 `PhpRedisClusterConnection::scan()` 在未指定节点时使用 `_masters()[0]`，本包不传节点参数，因此其余分片上的 key 扫不到、也不会被删除，**而方法仍然返回 `true`**。

这是已知且已接受的行为，不是缺陷：各集群数据不要求强一致，缓存 miss 可回源数据库，残留 key 会随 TTL 自然过期收敛。需要覆盖整个集群的清理时，请在未绑定的默认集群上使用 `scan_strategy => 'all_nodes'`。

因此**所有缓存写入都应设置合理 TTL**，不要依赖清理来回收，否则绑定集群场景下会留下无法回收的 key。

### 5. 统计只覆盖 `remember()`

`recordStats()` 只在 `remember()` 内部调用：命中记 `hits`，未命中记 `misses`。直接使用 `get()` / `set()` 的请求**完全不计数**。

如果业务里混用两种写法，`getStats()` 返回的 `hit_rate` 会严重低估真实命中率。做容量评估或告警阈值时要按这个口径解读，或统一收敛到 `remember()`。

### 6. 其余常规约束

- **数据大小**：单条缓存默认上限 1MB，超限直接不写入，`set()` 返回失败。
- **参数过滤**：默认开启 `force_validate`，会清洗参数中的 HTML 标签、SQL 关键字等内容。清洗是**有损**的，但缓存 key 里额外带了一份原始参数的指纹，因此不同的原始入参永远不会算出同一个 key。参数顺序始终不影响 key（递归 `ksort`），与 `force_validate` 是否开启无关。
- **gateway 名会被清洗**：只保留字母、数字、下划线和连字符，其余字符直接剔除。因此 `a/b c!` 与 `abc` 会算出相同的 key，命名时注意避免不同网关清洗后撞名。`clearGateway()` 使用同一套清洗规则，所以写得进去就清得掉，gateway 里的通配符也不会扩大删除范围。
- **加密**：依赖 Laravel 的 `encrypt` / `decrypt`，非 Laravel 环境自动跳过。
- **`shared_mode`**：设为 `true` 后 Redis 写失败时 `set()` 返回 `false` 且不写 LocalCache，不伪装成功；`mset()` 中失败的项同样返回 `false`。多实例严格共享部署必须开启。
- **`cluster_safe_mode`**：Redis Cluster 下建议保持 `true`，会把 `mget`、`mset`、标签清理、批量删除等多 key 命令降级为逐 key 操作，代价是网络往返次数上升，跨地域集群下批量操作耗时会明显增加。

## 五、四种部署形态的配置

先记住一条贯穿全文的判定规则：**`redis_cluster.enabled` 同时控制三件事**——是否给 key 加 hash tag、是否启用多 key 逐 key 降级、是否允许调用 `cluster()`。它不区分你后端接的是真 Redis Cluster 还是若干台独立 Redis 实例。理解这一点，下面四种形态的取值就都能推导出来。

| 形态 | 后端 | `enabled` | `cluster_safe_mode` | `scan_strategy` | 能否 `cluster()` 切换 |
| --- | --- | --- | --- | --- | --- |
| A | 单台 Redis | `false` | 不生效 | `single_connection` | 否 |
| B | 多台独立 Redis | `true` | `false` | `single_connection` | 是 |
| C | 单个 Redis Cluster | `true` | `true` | `all_nodes` | 用白名单禁止 |
| D | 多个 Redis Cluster | `true` | `true` | `all_nodes` | 是 |

### 形态 A：单 Redis 实例

最简单的形态，也是默认配置。

```php
// config/database.php
'redis' => [
    'client' => 'phpredis',
    'default' => [
        'host' => env('REDIS_HOST', '127.0.0.1'),
        'port' => env('REDIS_PORT', 6379),
        'password' => env('REDIS_PASSWORD'),
        'database' => 0,
    ],
],
```

```php
// config/request_cache.php
'cache' => [
    'strategy' => [
        'primary' => 'redis',
        'secondary' => 'array',
        'fallback' => true,
        'shared_mode' => true,  // 多台 PHP 机器共用这台 Redis 时建议开启
    ],
    'redis_cluster' => [
        'enabled' => false,
        'hash_tag' => null,
        'cluster_safe_mode' => false,
        'scan_strategy' => 'single_connection',
        'default_connection' => 'default',
        'connections' => [],
    ],
],
```

行为说明：

- key 不带 hash tag，前缀就是 `prefix` 的原值，例如 `my_app_cache:1.0:users:<hash>`。
- `isClusterSafeMode()` 要求 `enabled` 与 `cluster_safe_mode` 同时为真，所以 `enabled=false` 时这一项取什么值都不生效，`mget` / `mset` / 批量 `del` 一律走原生多 key 命令和 pipeline，性能最好。
- 调用 `cluster()` 抛 `LogicException`。
- `clearGateway()` / `clearAll()` 在当前连接上单次 SCAN，单实例没有分片，覆盖是完整的。

### 形态 B：多台独立 Redis 实例，手动切换

后端不是 Redis Cluster，而是若干台平级的独立 Redis，希望用 `cluster()` 指定本次操作落到哪一台（例如冷热分离、大对象独立存储、多地就近读）。

**关键前提：`enabled` 必须为 `true`。** `cluster()` 只检查 `redis_cluster.enabled`，与后端是否真的是 Redis Cluster 无关；`enabled=false` 时任何切换都会抛 `LogicException`。

```php
// config/database.php —— 连接平级放在顶层，不要放进 clusters
'redis' => [
    'client' => 'phpredis',
    'default' => ['host' => env('REDIS_HOST'), 'port' => 6379, 'database' => 0],
    'gz'      => ['host' => env('REDIS_GZ_HOST'), 'port' => 6379, 'database' => 0],
    'hk'      => ['host' => env('REDIS_HK_HOST'), 'port' => 6379, 'database' => 0],
],
```

```php
// config/request_cache.php
'redis_cluster' => [
    'enabled' => true,              // 必须 true，否则 cluster() 抛 LogicException
    'hash_tag' => 'request-cache',  // 单实例上 hash tag 无害，只是 key 里多一段 {request-cache}
    'cluster_safe_mode' => false,   // 单实例没有 CROSSSLOT 限制，关掉以保留原生 mget/mset/pipeline
    'scan_strategy' => 'single_connection', // 必须，理由见下方警示
    'default_connection' => 'default',
    'connections' => ['default', 'gz', 'hk'],
],
```

两条必须注意的点：

**第一，开启 `enabled` 就一定会带上 hash tag，无法只要切换能力而不要 hash tag。** `hash_tag` 留空只是改用默认的 `app_env_cache` 形式，并不会取消。单实例上这没有功能影响，但会改变 key 的字面形态。

**第二，这种形态下绝对不要设 `scan_strategy => 'all_nodes'`。** `all_nodes` 会去 `database.redis.clusters` 里按连接名找节点列表；顶层连接不在 `clusters` 中，找不到同名项时解析器会退而使用 `clusters['default']`，或者在只配了一个 cluster 时直接用那一个。结果就是 SCAN 扫到一套和数据实际所在完全无关的 Redis，而且这个误扫是静默发生的，清理会「成功」但什么都没删。项目里只要同时存在 `clusters` 配置，这个坑就会踩上。

### 形态 C：单个 Redis Cluster（关闭多集群切换）

后端是一套真正的 Redis Cluster，不需要运行时切换。

```php
// config/database.php
'redis' => [
    'client' => 'phpredis',
    'clusters' => [
        'options' => [
            'password' => env('REDIS_CLUSTER_PASSWORD'), // 密码放这里，不要塞进每个节点
        ],
        'default' => [
            ['host' => env('REDIS_NODE_1'), 'port' => 6379],
            ['host' => env('REDIS_NODE_2'), 'port' => 6379],
            ['host' => env('REDIS_NODE_3'), 'port' => 6379],
        ],
    ],
],
```

```php
// config/request_cache.php
'redis_cluster' => [
    'enabled' => true,
    'hash_tag' => 'request-cache',
    'cluster_safe_mode' => true,
    'scan_strategy' => 'all_nodes',
    'default_connection' => 'default',
    'connections' => ['default'],  // 只列一个 = 从配置层面关闭切换
],
```

**「关闭多集群」的正确做法是把 `connections` 收敛为单个连接名**，此后任何 `cluster('其他')` 都会抛 `InvalidArgumentException`，而 `cluster('default')` 等价于不切换。

**不要用 `enabled=false` 来关闭多集群。** 在真正的 Redis Cluster 上把 `enabled` 设为 `false`，会同时丢掉 hash tag 和 `cluster_safe_mode` 两层保护：缓存值、标签集合、统计和锁的 key 会散落到不同 slot，`mget` / `mset` / 批量 `del` 会直接触发 `CROSSSLOT Keys in request don't hash to the same slot` 错误。

### 形态 D：多个 Redis Cluster，手动切换

v1.0.5 的目标形态，配置见 [README 的多集群章节](../README.md#多-redis-集群手动切换)。

```php
'redis_cluster' => [
    'enabled' => true,
    'hash_tag' => 'request-cache',
    'cluster_safe_mode' => true,
    'scan_strategy' => 'all_nodes',   // 仅对 default 生效，绑定 gz/hk 时运行时自动降级
    'default_connection' => 'default',
    'connections' => ['default', 'gz', 'hk'],
],
```

## 六、形态之间切换的迁移影响

改动下列任何一项，都会**改变 key 的字面形态**，旧 key 立即变成读不到的孤儿数据，只能等 TTL 自然过期回收：

- `redis_cluster.enabled` 在 `true` / `false` 之间切换（决定 key 是否带 hash tag）。
- `hash_tag` 改名。
- `request_cache.prefix` 改动。
- `version` 改动（这本来就是它的设计用途）。

改动 `default_connection` 不改变 key 形态，但会改变数据的物理落点：旧连接上的数据不会迁移，表现为一次全量 miss，旧数据同样靠 TTL 回收。

因此形态切换应当在低峰期进行，并优先选择以下两种做法之一：切换前若干个 TTL 周期先把 `default_expire` 调短，让存量自然收敛；或者切换后立即在**旧配置**下执行一次 `clearAll(true)` 回收孤儿 key，再切到新配置。切换后不要指望用新配置去清理旧 key——前缀已经对不上，扫不到。

## 七、场景化使用示例

### 场景 1：接口结果缓存（最常见）

用 `remember()` 而不是 `get()` + `set()`，一是自带分布式锁能防击穿，二是只有 `remember()` 会计入命中统计。

```php
use HwlowellRequestCache\RequestCache;

public function detail(int $id)
{
    return RequestCache::remember('user_detail', ['id' => $id], function () use ($id) {
        return User::query()->with('profile')->findOrFail($id)->toArray();
    }, 600);
}
```

实测在真实集群上，4 个并发进程同时对同一个 key 调用 `remember()`，回调只会被执行 1 次，其余进程等待后直接读到缓存值。

### 场景 2：列表页缓存 + 按标签批量失效

```php
$cache = new RequestCache();

$data = $cache->tags('product', $category)->remember('product_list', [
    'category' => $category,
    'page' => $page,
], fn () => $this->queryProducts($category, $page), 300);

// 商品变更后按标签批量失效
$cache->clearTags('product');
```

标签只对紧随其后的**一次**写入生效，用完即清空。需要给多次写入打同一组标签时，每次都要重新调用 `tags()`。

> 1.0.5 之前 `page` 参数会被无条件归一到 `1`，导致第 2 页读到第 1 页的数据；同时 `tags()` 设置后不会清空，会持续附加到后续所有写入上。两个问题都已修复。

### 场景 3：冷热分离，大对象放独立 Redis（形态 B）

```php
// 热点小对象走默认实例
$user = RequestCache::remember('user', ['id' => $id], fn () => $this->loadUser($id), 600);

// 大 JSON 报表放到专用实例，避免挤占主实例内存
$report = RequestCache::cluster('bulk')->remember('report', ['month' => $month], function () use ($month) {
    return $this->buildMonthlyReport($month);
}, 3600);
```

注意大对象要确认没超过 `size_limit`（默认 1MB），超限会静默不写入，每次都回源。需要缓存更大的对象时显式放宽：

```php
$cache = new RequestCache();
$cache->sizeLimit(5 * 1024 * 1024); // 5MB
```

### 场景 4：多地部署，就近读 + 手动回填（形态 D）

兜底顺序、回填、超时全部由业务编排，本包不代劳。

```php
$params = ['id' => $id];

$data = RequestCache::get('users', $params);              // 本地集群

if ($data === null) {
    $data = RequestCache::cluster('hk')->get('users', $params); // 跨地域兜底
}

if ($data !== null) {
    RequestCache::cluster('default')->set('users', $params, $data, 600); // 回填本地
} else {
    $data = $this->loadFromDatabase($id);                 // 回源
    RequestCache::set('users', $params, $data, 600);
}
```

跨地域读取的 RTT 通常在几十毫秒量级，串行兜底会直接叠加到接口耗时上。建议只对少数关键接口启用兜底，并限制兜底集群的数量。

### 场景 5：多地删除，需要显式遍历

本包不提供删除广播，一致性由调用方保证。

```php
foreach (['default', 'gz', 'hk'] as $name) {
    RequestCache::cluster($name)->delete('users', ['id' => $id]);
}
```

`delete()` 的返回值**不能用来判断是否成功**：它的实现是 `return $redis->del($key) > 0`，异常时返回 `false`。也就是说「key 本来就不存在」和「Redis 不可达」都返回 `false`，两者无法区分。需要可靠的删除语义时，只能在业务侧自行探测连接可用性，或直接接受最终由 TTL 收敛。

无论 Redis 是否可达，`delete()` 都会先删掉本进程 LocalCache 中对应连接的那份副本，这一步不会失败。

### 场景 6：全量清理（只能在默认集群上做）

```php
// 正确：未绑定 + all_nodes，遍历 default_connection 对应集群的全部节点
RequestCache::clearAll(true);

// 错误：绑定后强制降级为 single_connection，只覆盖该集群第一个 master，
// 其余分片的 key 扫不到、删不掉，但方法仍然返回 true
RequestCache::cluster('hk')->clearAll(true);
```

需要清空某个非默认集群时，只能临时把 `default_connection` 指到它、在未绑定状态下执行，或者接受靠 TTL 收敛。

### 场景 7：Redis 故障时的行为选择

`shared_mode` 决定 Redis 写失败时是「本地兜底」还是「如实报错」，选择取决于业务能否容忍实例间数据不一致。

```php
// shared_mode = false：set() 返回 true，值写进当前进程的 LocalCache
// 适用于单机部署，或缓存内容允许各 worker 短时间不一致
// shared_mode = true：set() 返回 false，不写 LocalCache
// 适用于多实例严格共享，宁可回源也不要伪成功
$ok = RequestCache::set('users', ['id' => 1], $data, 600);

if (!$ok) {
    // shared_mode=true 且 Redis 不可用时会走到这里，按需降级或告警
    Log::warning('request cache write failed', ['id' => 1]);
}
```

实测在 Redis 完全不可达时，`get` / `mget` / `delete` / `remember` / `clearGateway` / `clearTags` / `getStats` 七个入口都返回安全值（分别是 `null` / 数组 / 布尔 / 回调结果 / 布尔 / 布尔 / 数组），不会抛异常穿透到业务代码，可以放心不加额外的 try-catch。

### 场景 8：整体换版发布

数据结构变更时不必逐个清理，换版即可让全部旧 key 失效。

```php
// 方式一：改配置，全局生效
'request_cache' => ['version' => '2.0'],

// 方式二：运行时改，注意会污染容器单例，应自建实例
$cache = new RequestCache();
$data = $cache->version('2.0')->get('users', ['id' => 1]);
```

旧版本的 key 不会被自动删除，靠 TTL 回收；如需立即回收，在换版**之前**执行 `clearAll(true)`。

## 八、常见配置错误对照

| 现象 | 直接原因 | 处理 |
| --- | --- | --- |
| `Couldn't map cluster keyspace using any provided seed` | 集群密码写在了各节点上，没写进 `clusters.options` | 密码移到 `clusters.options.password` |
| 调用 `cluster()` 抛 `LogicException` | `redis_cluster.enabled` 为 `false` | 置为 `true`；接独立 Redis 实例时同样需要 |
| 调用 `cluster()` 抛 `InvalidArgumentException` | 连接名不在 `connections` 白名单，或白名单自动推导没覆盖到 | 显式把连接名写进 `connections` |
| `CROSSSLOT Keys in request don't hash to the same slot` | 真集群上 `enabled` 或 `cluster_safe_mode` 为 `false` | 两项都置为 `true` |
| 清理返回 `true` 但 key 还在 | 绑定了非默认集群，只覆盖第一个 master；或形态 B 误开了 `all_nodes` 扫到了别的 Redis | 在未绑定的默认集群上用 `all_nodes`；形态 B 固定 `single_connection` |
| 命中率长期偏低且与体感不符 | 统计只覆盖 `remember()`，`get()`/`set()` 不计数 | 按此口径解读，或统一收敛到 `remember()` |
| 换配置后缓存全部 miss | 改动了 `enabled`、`hash_tag`、`prefix` 或 `version`，key 形态变了 | 属预期行为，旧 key 靠 TTL 回收，见第六节 |
| 某次链式调用后全局行为异常 | 通过 Facade 调用了 `version()`/`tags()`/`sizeLimit()` 等，污染了容器单例 | 改为自建实例，见第三节 |

## 九、升级检查清单

1. 确认 `default_connection` 指向的连接名在 `database.php` 中真实存在；默认值 `default` 保证了向后兼容，不改就是原有行为。
2. 显式列出 `connections` 白名单，避免自动推导把不该暴露的连接纳进来。
3. 检查是否有代码通过 Facade 调用 `version()` / `tags()` / `sizeLimit()` / `encryptData()`，这些会污染容器单例，改为自建实例。
4. 如果依赖 `clearGateway()` / `clearAll()` 做缓存回收，确认清理路径没有绑定非默认集群；绑定场景下必须靠 TTL 兜底。
5. 升级到 `c2553de` 之后，此前因 SCAN 游标问题而「看起来成功、实际没删」的清理会真正生效，首次执行可能删除远超预期数量的历史 key，建议先在非生产环境评估。
6. 回归 `CacheMonitor` 的调用点：`getHealthStatus()` 等方法此前在集群下会抛 `ArgumentCountError`，如果业务侧写了针对性的异常捕获，修复后行为会变化。
7. 按第五节对号入座核对当前形态：重点确认形态 B（多台独立 Redis）没有误开 `scan_strategy => 'all_nodes'`，形态 C/D（真集群）的 `cluster_safe_mode` 保持 `true`。
8. **缓存 key 算法与存储格式在本次修复中都变了**，升级即等同一次全量换版：所有历史 key 读不到，旧值靠 TTL 回收，详见第十节。请在低峰期发布，并确认回源链路能承受一次冷启动。

## 十、本轮缺陷修复带来的行为变化

以下改动均已合入，逐条说明升级后会看到什么变化。

### 会改变缓存 key 与存储格式（升级即全量失效）

- **缓存 key 现在带原始参数指纹。** 此前 key 只由清洗后的参数算出，而清洗是有损的：数值被钳制到 ±1,000,000（`id=1000001` 与 `id=99999999` 生成同一个 key）、SQL 关键字被整词删除（`q=order`、`q=and`、`q=` 三者同 key）、非字母数字字符被删除、超过 1000 字符被截断。这些都会让不同请求读到彼此的缓存。现在 key 中额外包含原始参数的 SHA-256 指纹，不同入参永远不会撞 key。
- **移除了 `page` 的无条件归一。** 此前 `page != 1` 会被改写成 `page = 1`，翻页读到第 1 页数据。现在 `page` 与普通参数一视同仁。
- **参数排序改为递归且不再依赖 `force_validate`。** 嵌套数组同样按键名排序，参数顺序在任何配置下都不影响 key。
- **Redis 中的值改为带版本信封**（`{"v":1,"d":<数据>,"e":<绝对过期时间>}`）。读取时兼容旧的裸 JSON，因此回滚不会读到乱码；但新旧 key 本来就对不上，实际影响是一次全量冷启动。

### 会改变返回值与语义

- **`mget()` 返回稠密数组。** 未命中项现在填 `null` 占位，下标与入参一一对应；此前未命中项直接缺失，按下标取值会撞未定义索引。
- **`remember()` 现在能缓存 `null` 和 `0`。** 此前 `get()` 用真值判断，`json_encode(0)` 得到的 `"0"` 是 PHP 假值，导致数值 0 永远读不回；空结果也无法缓存，形成穿透。信封格式配合新增的内部条目判定解决了这两点。
- **`tags()` 用后即清。** 标签只对紧随其后的一次写入生效，不会再泄漏到同一实例的后续写入。
- **`clearGateway()` 会先清洗 gateway。** 含 `/`、空格等字符的 gateway 此前写得进去却清不掉（且返回 `true`）；gateway 里的 `*` `?` `[` 此前会直接进入 SCAN pattern 扩大删除范围。现在与 `generateKey()` 使用同一套规则，清洗后为空则直接返回 `false`。

### 会改变运行时行为

- **本地缓存副本不再比 Redis 的值活得更久。** 此前 Redis 命中后回填本地缓存不带 TTL，一律按 `local_cache.ttl`（默认 300 秒）存活，常驻进程（Octane、Swoole、队列 worker）会在 Redis key 过期后继续返回旧值最长 300 秒。现在信封里带绝对过期时间，本地 TTL 取二者较小值。
- **清理改为边扫描边删除。** 此前先把 key 收集到内存再删，累计超过 10000 条就 `break`，超出部分静默漏删且仍返回 `true`（实测 10500 条只删掉约 9000 条）。现在按批流式删除，不再有上限，内存占用也是恒定的。
- **`cache.lock` 配置终于生效。** 此前 `getLockConfig()` 零调用，`acquireLock()` 用的是硬编码的 `expire=10 / retry_times=5 / retry_delay=100000`，与配置文件里写的值不符。现在 `expire`、`retry_times`、`retry_delay` 都从配置读取。
- **抢锁失败不再立刻回源。** 此前重试窗口（约 2.5 秒）耗尽后直接执行回调，回调耗时超过该窗口时防击穿完全失效（实测 4 秒回调、3 个进程，回调执行了 3 次）。现在会继续轮询缓存直到锁自然过期或持锁者退出，拿到结果就直接返回。
- **RediSearch 相关方法不再抛致命错误。** `search()` 等 10 个方法依赖的 `RediSearchService` 并不在本包内，此前会抛出 `Error`，而方法体只 `catch (\Exception)`，异常会穿透到业务代码。现在缺失时按各方法既定的降级值返回。

### 已知但本轮未处理

- **`renewLock()` 仍无调用点**，`cache.lock.enable_extend` 与 `extend_interval` 两项配置仍然不生效。回调耗时超过锁 TTL 时，锁会自然过期并允许另一个进程进入。请把 `lock.expire` 设得比最慢的回调更长。
- **统计仍只覆盖 `remember()`**，`get()` / `set()` 不计数。
- **`delete()` 的返回值仍不能区分「key 不存在」与「Redis 不可达」**，两者都返回 `false`。
- **传入带 `cache` 段的自定义配置构造实例，仍会改写全局静态配置**（`CacheConfig` 的策略、本地缓存、锁、统计、集群配置都是静态属性）。只传 `request_cache` 段不受影响。
- **`mset()` 的 pipeline 分支不检查 `exec()` 的逐条结果**，仍然乐观标记为成功。
